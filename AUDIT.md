# Audit guide — can the BUY-IN operator cheat?

This guide is written for independent reviewers, human or AI. It lists what to fetch, what to recompute, and what the result means. You do not need to trust the operator for any step.

**Live engine (read this first):** https://tee.buyinholdem.com/
(same TEE, also at the Phala gateway address https://5edf839d04a49add7001648a6bc226292f0fd968-3900.dstack-pha1-prod5.phala.network/)
It is a plain-text report generated by the engine from inside the TEE, with links to the raw JSON.

## 1. What is being claimed

BUY-IN is a private hold'em service. The claim is narrow and checkable:

> During a hand nobody — including the operator — can see hidden cards, choose the deck, act for a player, or change the result; and every finished hand can be re-computed by anyone.

The claim rests on three pieces, all public:

| Piece | Where | What it proves |
|---|---|---|
| Engine source | this repository | the rules, the shuffle, the hole-card encryption, the record format |
| Reproducible image | GitHub Actions → `ghcr.io/buyinofficial/buyin-engine@sha256:…` | the image is exactly this source |
| TEE attestation | engine `/info`, `trust.phala.com/app/<appId>` | that image runs inside Intel TDX and owns the signing key |

## 2. Step-by-step checks

Fetch `GET <engine>/info`. Then:

1. **Genuine hardware.** `POST https://cloud-api.phala.com/api/v1/attestations/verify` with `{"hex": attestation.quote}` → `success: true`, `quote.verified: true`. Independent option: Intel DCAP via `dcap-qvl`.
2. **Key bound to the TEE.** `quote.body.reportdata` (or bytes 568–600 of the raw quote) must equal `SHA-256(stableStringify({ ecdh, sig }))` over `keys.ecdh` and `keys.sig` (each reduced to `{crv,kty,x,y}`, keys sorted). Code: `src/attest.js` `reportDataFor`, `checkInfoBinding`. The private keys are generated inside the TEE and never exported.
3. **Measured configuration = published configuration.** `SHA-256(attestation.appCompose)` must equal `attestation.composeHash`. The TEE measures this hash into RTMR3 at boot; Phala's report replays the event log to show it. `appCompose` contains `deploy/docker-compose.yml`, which pins the image by digest.
4. **Image = source.** Rebuild the tag named in `/info` (`v<version>`) as described in the README ("Rebuild the image yourself"). The digest must equal the one pinned in the compose. The CI log of the tag build prints the same digest.
5. **Results come from this engine.** Every hand ends with a record signed by `keys.sig`. `node src/verify.js record.json key.json` checks the signature, the seed against the pre-hand commitment, the shuffle against the players' random values, all 52 card commitments, and replays every action under `HandCore` — any difference fails.
6. **Records are not rewritten.** The engine appends each record to a hash chain on the TEE's encrypted disk (`src/store.js`) and sends each line to the console (`src/outbox.js`). `GET /records/head` returns `{count, head, first, sent}`; `count` only grows. Lines older than `TEE_RETENTION_DAYS` (7) that were already sent are deleted; the console keeps them with the engine's signature. `GET /records/keys` lists the engine keys.
7. **The game uses this engine.** The table page is served by the TEE and checks that the engine key is the attested key from `/info`. (Engine keys change on every engine restart; each one is in `/records/keys` with its attestation `report_data`.)
8. **Server state = repository.** The measured deployment file (`appCompose.docker_compose_file`) is byte-for-byte `deploy/docker-compose.yml` of a commit in this repository; `appCompose.allowed_envs` is only `TEE_RPC_TOKEN` (the one secret, encrypted); there is no pre-launch script; the OS image reported in `vm_config` equals `deploy/tee-os.txt`. A `dstack-dev-*` image is a development image: the operator can open an SSH debug shell, so the claims in §3 assume a production image.

`node tools/check-deployment.js <engine>` in a checkout of the engine commit runs steps 1–4 and 8 and compares every loaded file.

## 3. Threat model

### The operator cannot

| Attack | Why it fails | Code |
|---|---|---|
| Look at hole cards or the undealt board | Cards exist only in the TEE. Hole cards leave encrypted to the player's browser key (ECDH P-256 → HKDF → AES-256-GCM). Board cards are released only when the betting round is over. | `crypto.js`, `HandCore.advance` |
| Pick or re-roll the deck | `SHA-256(seed)` is committed before the hand; players add signed random values; shuffle = `HMAC-SHA256(seed, …)`. A started hand consumes the commitment even if voided. | `cards.js`, `Engine.startHand` |
| Swap a card mid-hand | 52 card commitments are published at hand start; each revealed card comes with its salt and is checked in the browser. | `cards.js` |
| Bet, call or raise for a player | Chip-moving actions need the player's ECDSA signature bound to this hand and turn. The operator can only fold/check (timeouts), and the record marks each one. | `HandCore._authorize` |
| Move chips between players outside a hand | Only a tip does this: 1 big blind, signed by the sender (`msgTip`, a per-seat number so a signature works once), moved after the hand ends and written to the record chain with the signature and the sender's public key. | `TableServer._tip`, `_settleTips` |
| Change results or rake | The engine computes pots, winners and rake from the published table rule; the signed record replays exactly. | `HandCore`, `verify.js` |
| Delete or edit past hands | Records are signed and chained on the TEE disk; the chain head is public. | `store.js` |
| Run a modified engine | A modified image has a different digest → different compose hash → a different attestation; it cannot produce a key bound to this measurement. | §2 steps 2–4 |
| Read the engine's memory | Intel TDX encrypts and isolates the VM memory from the host. | hardware |

### The operator still controls

- Who may join a table, connection handling (it can disconnect a player; the engine then folds/checks for that seat and the record shows it), wallets, deposits and withdrawals.
- Account identity — logins are run by the operator. Collusion between accounts (sharing cards outside the game) is not something a game engine can prevent; it is analysed after the fact from the signed records.
- Availability — the operator can stop the service. It cannot make a running hand come out differently.

### Trust that remains

- Intel TDX hardware and Intel's attestation signing keys.
- Phala Cloud's dstack OS image and KMS (measured; see `trust.phala.com`). On a development OS image (`dstack-dev-*`, see `deploy/tee-os.txt`) the operator can open an SSH debug shell into the VM; the guarantees above need a production image.
- The correctness of this source code — which is exactly why it is public.

## 4. What the operator's systems see, and when

Since 0.5.x every hand runs in the TEE table server (`src/table/`, "table mode", on when `TEE_CONSOLE_KEY` is set in the measured compose). The operator's servers issue seat tickets and pay out; they are not on the game path.

| When | Operator (game server, admin console) can see | Operator cannot see |
|---|---|---|
| Sitting down | the buy-in it took and the seat ticket it signed | the player's keys or table session token |
| During a hand | nothing from the engine — the engine has no operator route (`src/server.js`), and the running hand is not yet in the record chain | — |
| After the hand ends | the full signed record (every hole card, seed, deck, action), sent by the engine to the console (`src/outbox.js`); the console's check API (`src/consoleApi.js`, token) returns finished hands only | — |
| Leaving | the engine-signed settlement note (amounts only) | — |

The engine writes a record only when the hand is closed (`Engine._closeHand`), `test/server.test.js` checks that there is no operator route (`/rpc` and record export are 404), and `test/results.test.js` checks that a hand in play is not in the record store or the check API. The engine prints no cards to its logs.

## 5. The player's browser

The browser code that holds the player's keys and opens the hole-card envelope is served by the TEE itself (`src/public/table/js/vault.js`, `app.js`):

- The player's keys are WebCrypto keys created in the browser and stored as non-extractable keys; only the public keys are sent.
- The envelope is opened with ECDH (player key × engine key) → HKDF-SHA256 → AES-256-GCM, inside the browser.
- Every revealed card is checked against the 52 commitments published at hand start.
- The page checks that the engine key is the attested key (`/info`).

Images, sounds and videos are loaded from the console's resource server (`https://resource.buyinholdem.com/buyin-table/`, allowed by the page's CSP for images, plus the `sfx/` folder for sound files and the `emo/` and `fx/` folders for emote and all-in videos). Which file is loaded never depends on a card: card faces are drawn as text, chips show public bet amounts, sounds follow public actions, emotes are what a player picked. The page's scripts, styles and **the font that draws the card ranks and suits** (`src/public/table/font/`, CSP `font-src 'self'`) all come from the TEE, so the operator cannot change how a card looks. The design files themselves are not in this repository, but their SHA-256 are: `resources.sha256`; `node tools/check-resources.js` downloads each one from the resource server and compares.

Emotes, chat, the time bank, the "raising…" hint and the in-the-dark reservation are handled by the TEE table server (`TableServer._emote`, `_chat`, `_timeBank`, `_raising`, `_dark`) and only relayed to the seats of the same table: the TEE does not store, log or send them to the console, and they never touch cards or chips. One exception the page itself makes: to translate chat, the browser sends the text of a chat line it received (only that text and the reader's language) to the operator's translation address `https://buyinholdem.com/chat-translate` (`app.js` `translateLine`, allowed by `connect-src`). Chat is therefore not private from the operator; cards and game data are never sent there. "Raising…" is sent only by the player whose turn it is, while they move the bet slider. In the dark hides the player's own two cards on their own screen for one hand (the TEE still deals and sends them as usual, and the page shows them after the hand). A time-bank chip (3 per seat, one per turn, +20 s) only moves the turn deadline. Tips are different because chips move: see the table above (`_tip`).

## 5a. Pages served by the TEE (0.5.0)

These files are in this repository (`src/public/table/`), are inside the attested image, and are served by the engine at its own address — the operator cannot change them without changing the image digest and therefore the attestation.

- **`/table/`** — the table. The browser talks only to the TEE: `connect-src 'self'` (plus GET of fixed sound files from the resource server's `sfx/` folder and POST of received chat lines to the translation address), `frame-ancestors 'none'` (no operator page can wrap it). A seat ticket signed by the console key (`TEE_CONSOLE_KEY`, public JWK in the measured compose) brings the player in; cards, turns and results come from the TEE over SSE; actions go back signed with the player's key. The operator receives only settlement notes (amounts, engine-signed) and, after each hand, the signed record.
- **`/table/verify.html`** — Verify my hands. With the key in the player's browser it asks the TEE for that player's hands (`POST /records/mine`, signature over `["pz-mine-v1", keyFingerprint, time, handId]`, five-minute window; only hands where that key held a seat). For a chosen hand it checks, in the browser:
  1. the chain line hash and the public receipt `/records/receipt/<handId>`;
  2. the engine key line in the chain and its TDX `report_data` (and the live quote for the current key);
  3. a full replay with **the engine's own files** (`/table/engine/*.js` — the repository files wrapped in one line so a script tag can load them; signatures are collected during the replay and then checked with WebCrypto);
  4. the hole cards the browser opened during the hand against the record.
  Tampering with a stack, an action signature or the deck makes the replay fail (tested).

## 6. Reporting

Security issues: open a private security advisory on this repository. Fixes are released with a new tag, image digest and attestation.

### Outbound connections of the engine

1. `src/outbox.js` — lines of the record chain (finished hands only) to `TEE_CONSOLE_URL` in the measured compose.
2. `src/explorer.js` — at start, its own TDX quote (public) to the Phala TEE Attestation Explorer (https://proof.t16z.com), so the audit report can link an independent verification of the running engine. Nothing else is sent.

### Public table record (0.9.19)

`GET /records/table/<tableId>` and `/records/table/<tableId>.html` list every finished hand of one table from the TEE's own hash chain: seat numbers, chips at the start and end of each hand, rake, chain line and receipt link. No cards, deck, seed or member numbers. A player (or an AI they ask) compares the game record the operator showed them with this page, value by value.
