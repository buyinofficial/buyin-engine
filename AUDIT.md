# Audit guide — can the BUY-IN operator cheat?

This guide is written for independent reviewers, human or AI. It lists what to fetch, what to recompute, and what the result means. You do not need to trust the operator for any step.

**Live engine (read this first):** https://b51e283808f74696162569696b1af768340cd054-3900.dstack-pha1-prod5.phala.network/
It is a plain-text report generated by the engine from inside the TEE, with links to the raw JSON.

## 1. What is being claimed

BUY-IN is a private hold'em service. The claim is narrow and checkable:

> During a hand nobody — including the operator — can see hidden cards, choose the deck, act for a player, or change the result; and every finished hand can be re-computed by anyone.

The claim rests on three pieces, all public:

| Piece | Where | What it proves |
|---|---|---|
| Engine source | this repository | the rules, the shuffle, the hole-card encryption, the record format |
| Reproducible image | GitHub Actions → `ghcr.io/buyinofficial/buyin-engine@sha256:…` | the image is exactly this source |
| TEE attestation | engine `/info`, `trust.phala.com/app/<appId>` | that image runs inside Intel TDX and owns the signing key |

## 2. Step-by-step checks

Fetch `GET <engine>/info`. Then:

1. **Genuine hardware.** `POST https://cloud-api.phala.com/api/v1/attestations/verify` with `{"hex": attestation.quote}` → `success: true`, `quote.verified: true`. Independent option: Intel DCAP via `dcap-qvl`.
2. **Key bound to the TEE.** `quote.body.reportdata` (or bytes 568–600 of the raw quote) must equal `SHA-256(stableStringify({ ecdh, sig }))` over `keys.ecdh` and `keys.sig` (each reduced to `{crv,kty,x,y}`, keys sorted). Code: `src/attest.js` `reportDataFor`, `checkInfoBinding`. The private keys are generated inside the TEE and never exported.
3. **Measured configuration = published configuration.** `SHA-256(attestation.appCompose)` must equal `attestation.composeHash`. The TEE measures this hash into RTMR3 at boot; Phala's report replays the event log to show it. `appCompose` contains `deploy/docker-compose.yml`, which pins the image by digest.
4. **Image = source.** Rebuild the tag named in `/info` (`v<version>`) as described in the README ("Rebuild the image yourself"). The digest must equal the one pinned in the compose. The CI log of the tag build prints the same digest.
5. **Results come from this engine.** Every hand ends with a record signed by `keys.sig`. `node src/verify.js record.json key.json` checks the signature, the seed against the pre-hand commitment, the shuffle against the players' random values, all 52 card commitments, and replays every action under `HandCore` — any difference fails.
6. **Records are not removed or rewritten.** The engine appends each record to an append-only hash chain on the TEE's encrypted disk (`src/store.js`). `GET /records/head` returns `{count, head}`; save it and compare later — the chain can only grow, and `GET /records/keys` lists every engine key the chain has used.
7. **The game uses this engine.** In the game, the player's browser compares the engine key it receives from the game server with the attested key it fetches directly from `/info`. A mismatch is shown to the player. (Engine keys change on every engine restart; each one is in `/records/keys` with its attestation `report_data`.)

## 3. Threat model

### The operator cannot

| Attack | Why it fails | Code |
|---|---|---|
| Look at hole cards or the undealt board | Cards exist only in the TEE. Hole cards leave encrypted to the player's browser key (ECDH P-256 → HKDF → AES-256-GCM). Board cards are released only when the betting round is over. | `crypto.js`, `HandCore.advance` |
| Pick or re-roll the deck | `SHA-256(seed)` is committed before the hand; players add signed random values; shuffle = `HMAC-SHA256(seed, …)`. A started hand consumes the commitment even if voided. | `cards.js`, `Engine.startHand` |
| Swap a card mid-hand | 52 card commitments are published at hand start; each revealed card comes with its salt and is checked in the browser. | `cards.js` |
| Bet, call or raise for a player | Chip-moving actions need the player's ECDSA signature bound to this hand and turn. The operator can only fold/check (timeouts), and the record marks each one. | `HandCore._authorize` |
| Change results or rake | The engine computes pots, winners and rake from the published table rule; the signed record replays exactly. | `HandCore`, `verify.js` |
| Delete or edit past hands | Records are signed and chained on the TEE disk; the chain head is public. | `store.js` |
| Run a modified engine | A modified image has a different digest → different compose hash → a different attestation; it cannot produce a key bound to this measurement. | §2 steps 2–4 |
| Read the engine's memory | Intel TDX encrypts and isolates the VM memory from the host. | hardware |

### The operator still controls

- Who may join a table, connection handling (it can disconnect a player; the engine then folds/checks for that seat and the record shows it), wallets, deposits and withdrawals.
- Account identity — logins are run by the operator. Collusion between accounts (sharing cards outside the game) is not something a game engine can prevent; it is analysed after the fact from the signed records.
- Availability — the operator can stop the service. It cannot make a running hand come out differently.

### Trust that remains

- Intel TDX hardware and Intel's attestation signing keys.
- Phala Cloud's dstack OS image and KMS (measured; see `trust.phala.com`).
- The correctness of this source code — which is exactly why it is public.

## 4. Reporting

Security issues: open a private security advisory on this repository. Fixes are released with a new tag, image digest and attestation.
